# Public Submission API Security Analysis

**Date:** 2026-08-27  
**Status:** Analysis only — no security fix is implemented by this document  
**Observed endpoint:** `POST /form-builder/api/submissions` (application route: `POST /api/submissions`)  
**Primary finding:** Public submissions can be created by calling the API directly, without rendering or completing the browser UI.

> This document intentionally separates expected public-API behavior from actual security bypasses. Applying authentication to every submission request would break anonymous public forms and is not the correct blanket fix.

---

## 1. Executive summary

A browser is only one possible HTTP client. Postman, `curl`, mobile applications, scripts, and bots can send the same request. Therefore, a backend cannot reliably enforce “the user must have used our page.” It can only enforce server-verifiable security and business conditions.

For a normal anonymous public form, a direct API request is **expected architecture**, not by itself an authentication vulnerability. The API must remain reachable for the public page to work.

The repository does, however, contain real security and business-logic gaps around this endpoint:

1. **Form authentication is enforced only in the frontend.** The backend submission service does not verify an authenticated respondent session. A direct request bypasses the email/phone gate.
2. **The displayed OTP is currently client-side and accepts the hardcoded value `1234`.** It provides no identity proof.
3. **The math CAPTCHA is generated by the client and the client submits both the problem and answer.** An API client can invent a solvable challenge.
4. **Payment is orchestrated after submission in the browser.** The backend accepts the submission before any trusted payment confirmation and does not record or verify payment state. A direct API request bypasses payment.
5. **Unknown field IDs are retained and stored.** Server validation checks configured fields but starts by copying every submitted key into the final data object.
6. **The Zod request schema exists but is not attached to the Express submission route.** GCP and Lambda entry points also pass unvalidated bodies into the service.
7. **The public JSON limit is 50 MB.** This materially increases denial-of-service and storage-abuse exposure.
8. **Rate limiting is incomplete and deployment-dependent.** Express has an in-memory, IP-only limit; equivalent controls are not visible in the GCP/Lambda handlers.

### Severity conclusion

| Form configuration | Assessment |
| --- | --- |
| Published, anonymous form with no payment | Direct API access is expected; spam/data-integrity exposure is **High** without stronger abuse controls |
| `authentication.enabled = true` | Direct submission is an authentication/business-flow bypass: **Critical** |
| `payment.enabled = true` | Direct submission can create an accepted-looking response without verified payment: **Critical** |
| `reCaptcha = true` | Existing client-generated challenge is bypassable: **High** |
| Voting, assessment, or unique-field workflows | Programmatic/race abuse can undermine result integrity: **High**, depending on use |

The screenshot showing `201 Created` proves the endpoint accepts the supplied request. Whether that individual request is an expected anonymous submission or a critical bypass depends on the form's authentication, payment, CAPTCHA, and duplicate-prevention settings.

## 2. What the current request path does

The production-looking URL is likely reverse-proxied to the Express route below:

```text
POST /api/submissions
  -> backend/src/routes/submission.routes.ts
  -> backend/src/controllers/express/submission.controller.ts
  -> backend/src/service/submission.service.ts
  -> backend/src/lib/validation.ts
  -> SubmissionDao
  -> MySQL / Firestore / MongoDB implementation
```

Equivalent public creation handlers also exist for:

- Google Cloud Functions: `backend/src/controllers/gcp/submission.gcp.ts`
- AWS Lambda: `backend/src/controllers/lambda/submission.lambda.ts`

All three entry points call the same `createSubmission` service without respondent authentication.

### Existing protections that are working

The service currently checks:

- The form exists.
- The form is published.
- `settings.isFormActive` is not false.
- The form has not passed `expirationDateTime`.
- Configured required fields and many configured field rules.
- Configured external validation.
- Configured unique fields, using an application-level lookup.
- Voting duplicate rules, when configured.
- An Express rate limit of 100 requests per 15 minutes per resolved IP.
- Basic string trimming and partial XSS sanitization.

These checks mean the endpoint is not a completely unrestricted database insert. They do **not** prove respondent identity, payment, a genuine CAPTCHA result, browser interaction, or legitimate human intent.

## 3. Why Postman cannot simply be blocked

The browser eventually sends an HTTP request. A user can inspect that request in browser developer tools and reproduce it in Postman. The following controls do not establish that the official UI was used:

- CORS
- `Origin` or `Referer` checks
- A static API key embedded in JavaScript
- A hidden field containing a constant value
- A custom header added by the frontend
- Obfuscated field names
- Disabling the submit button in the browser
- Client-side validation

CORS is a browser policy. Postman and server-side scripts do not enforce it. Origin checks may be useful as an additional signal, but they are spoofable outside a browser and can break legitimate embeds.

The correct design is to enforce every important condition on the server and use layered anti-automation controls.

## 4. Confirmed weaknesses in the current implementation

### 4.1 Client-side-only form authentication

**Relevant code**

- `src/pages/PublicFormPage.tsx`
- `backend/src/service/submission.service.ts`

The public page stores its authentication state in `sessionStorage`. The submission request contains only:

```json
{
  "formId": "...",
  "data": {},
  "captchaProblem": "...",
  "captchaAnswer": "..."
}
```

No server-issued respondent session or identity proof is sent. The backend does not inspect `settings.authentication` before creating the submission.

**Example impact**

A form configured to require email or phone verification can still return `201 Created` when a caller directly supplies valid field values to `/api/submissions`.

**Classification**

- CWE-602: Client-Side Enforcement of Server-Side Security
- OWASP API6: Unrestricted Access to Sensitive Business Flows
- Potential CWE-306: Missing Authentication for a Critical Function, when the form explicitly requires identity

### 4.2 Hardcoded OTP

`PublicFormPage.tsx` currently accepts `1234` and simulates sending it with a timeout. The OTP is neither generated nor verified by the backend.

This is not a production authentication mechanism. It allows impersonation of any email address or phone number entered in the UI and is completely absent from direct API calls.

### 4.3 Client-controlled CAPTCHA

The frontend generates a string such as `4 + 5`, calculates the answer, and sends both values. The backend recomputes the answer from the caller-supplied problem.

An API caller can submit a self-selected pair:

```json
{
  "captchaProblem": "1 + 1",
  "captchaAnswer": "2"
}
```

The server confirms only that the two attacker-controlled values agree. It does not prove a challenge was issued by the server or completed by a human.

### 4.4 Payment flow can be bypassed

The public page creates the SifyForms submission first and then calls the external Payment Orchestration Service from the browser. The SifyForms backend payment routes are `410 Gone` stubs, and the `Submission` model has no payment state.

Consequences:

- A direct API request creates a stored response without initiating payment.
- Admin users cannot reliably distinguish paid from unpaid submissions in the SifyForms database.
- Browser callbacks can fail after the response is already accepted.
- Analytics and downstream processing may include unpaid entries.

This is a business-logic integrity issue, not merely bot spam.

### 4.5 Request schema is not enforced at the route boundary

`CreateSubmissionSchema` exists in `backend/src/schemas/submission.schema.ts`, but `submission.routes.ts` does not use `validate(CreateSubmissionSchema)`.

Additionally:

- `data` is `z.record(z.string(), z.any())` with no field/value limits.
- The object is not declared strict.
- `validate.middleware.ts` calls `schema.parse(req.body)` but does not assign the parsed result back to `req.body`; schema transforms/defaults/stripping would therefore not reach the controller.
- GCP and Lambda handlers do not use this middleware.

A fix must validate inside a shared service boundary or apply equivalent validation to every deployment adapter.

### 4.6 Unknown field injection

`validateSubmission` begins by copying every key from `submittedData` into `data`. It validates configured fields afterward but returns the full copied object.

Therefore, this can be stored:

```json
{
  "known_field_id": "valid value",
  "not_in_form_schema": "attacker-controlled extra value"
}
```

Potential consequences:

- Pollution of JSON/CSV exports.
- Unexpected fields in administrative review screens.
- Additional input reaching assessment, voting, calculation, or integration code.
- Larger stored records.
- Future vulnerabilities if a downstream feature treats a reserved key as trusted metadata.

The server should build the stored object from the current schema's allowed field IDs, rather than copying the request and attempting to remove bad content later.

### 4.7 Nested values are not recursively normalized

Top-level strings and direct string array values are sanitized. Strings nested inside table rows or arbitrary objects are not recursively normalized. React normally escapes text, but this creates inconsistent trust boundaries for exports, integrations, calculations, and any future HTML rendering.

Input validation should be type-aware and recursive for supported structures. Output encoding must still be applied at each rendering/export destination.

### 4.8 Resource-consumption exposure

The Express app accepts JSON and URL-encoded bodies up to 50 MB. A public caller can repeatedly force parsing, validation, external-validation calls, uniqueness scans, JSON serialization, and database writes.

The current 100-per-15-minute limit is:

- In-memory by default, so it does not coordinate across replicas.
- Shared across all submission routes, including protected submission-management calls.
- IP-only.
- Not visibly duplicated in the Lambda/GCP handlers.
- Dependent on correct reverse-proxy IP configuration.

This maps to OWASP API4 (Unrestricted Resource Consumption) and API6 (Unrestricted Access to Sensitive Business Flows).

### 4.9 Duplicate and uniqueness checks are race-prone

Unique field and voting duplicate checks read existing records and insert afterward. Two concurrent requests can pass the read before either writes. Only a database uniqueness constraint or transactionally reserved key reliably prevents the race.

### 4.10 File references are not bound to a submission session

Submission validation accepts file-reference-shaped objects and checks caller-supplied metadata such as filename, MIME type, and size. The submission path does not prove that each referenced DMS object:

- Was initiated for this form and field.
- Was confirmed by the same respondent session.
- Is active and owned by the correct organization.
- Has passed malware scanning.

This should be addressed when submission sessions are introduced.

## 5. Recommended target architecture

### 5.1 Keep anonymous forms public

Do **not** require every respondent to have a SifyForms/Keycloak account. That would break public surveys, registrations, embedded forms, QR-code forms, and anonymous feedback.

Instead, support explicit form access modes:

1. `ANONYMOUS` — no identity requirement; anti-abuse controls still apply.
2. `VERIFIED_IDENTITY` — server-verified email/phone session required.
3. `AUTHENTICATED_USER` — Keycloak login required, if the product needs internal-only forms.
4. `PAID` — server-verified payment state required before a response becomes accepted.
5. `INTEGRATION` — separate authenticated API-key/service-account endpoint for approved machine submissions.

### 5.2 Use a public submission session / intent

Recommended flow:

```text
1. Client loads a published form.
2. Server issues a short-lived public form session.
3. Required OTP/CAPTCHA/payment prerequisites are attached to that server session.
4. Client submits data with an opaque, short-lived submission token.
5. Server verifies token purpose, form ID, expiry, one-time ID, and prerequisites.
6. Server validates and stores only schema-approved data.
7. The token/idempotency key is consumed atomically.
```

A session token alone does not stop Postman for anonymous forms; an API client can request one. Its value is that security-sensitive prerequisites become server-verifiable and bound to one form and one submission attempt.

Suggested token claims:

- `purpose: "form_submission"`
- `formId`
- `sessionId` / `jti`
- `schemaVersion`
- `identityType` and a non-reversible identity reference, when verified
- `captchaVerifiedAt`
- `paymentAttemptId`, when required
- `iat` and short `exp`

Store only a hash of opaque tokens when possible. One-time use must be enforced in Redis or the database; a signed JWT without state can otherwise be replayed until expiry.

### 5.3 Replace the math CAPTCHA

The easiest industry-standard change is Cloudflare Turnstile or hCaptcha:

- The browser receives a short-lived challenge token.
- The backend validates it directly with the provider using a secret not exposed to the client.
- Reject missing, expired, hostname-mismatched, replayed, or invalid tokens.
- Bind validation to the form/session and resolved client IP where appropriate.

Turnstile tokens are short-lived and server-side validation is mandatory. CAPTCHA should be combined with rate limits; it is not a complete anti-abuse system by itself.

### 5.4 Move OTP to the backend

Recommended endpoints:

```text
POST /api/public/forms/:formId/auth/start
POST /api/public/forms/:formId/auth/verify
```

Implementation requirements:

- Generate a cryptographically random OTP server-side.
- Store only an OTP hash.
- Expire it in 5–10 minutes.
- Limit sends and verification attempts by form, identity, session, and IP.
- Return generic responses to reduce identity enumeration.
- Use an email/SMS provider.
- On success, mark the public form session verified and issue/refresh the submission token.
- Never use the main Keycloak user table merely to represent anonymous respondents.

### 5.5 Make payment server-authoritative

Recommended state machine:

```text
PENDING_PAYMENT -> PAID -> ACCEPTED
                -> FAILED / EXPIRED
```

The backend should:

1. Calculate the payable amount from trusted form configuration and validated values.
2. Create a pending submission/payment attempt.
3. Create the provider order from the backend or trusted POS service.
4. Verify a signed provider webhook or server-to-server status response.
5. Atomically transition to `PAID` and then `ACCEPTED`.
6. Exclude pending/failed submissions from standard analytics, assessments, voting, notifications, and exports unless explicitly requested.

A browser redirect or callback must never be the source of truth for successful payment.

### 5.6 Strict, schema-derived input validation

Recommended public endpoint shape:

```text
POST /api/public/forms/:formId/submissions
```

Put `formId` in the route, not the request body, and validate:

- Strict top-level keys.
- Content type `application/json`.
- A small maximum body size (for example 256 KB–1 MB when files use DMS).
- Maximum field count.
- Maximum string/array/table sizes.
- Per-field runtime type based on the saved form schema.
- Only field IDs in the current published schema.
- Visibility/conditional rules on the server.
- Required/rule/external validations on the server.
- DMS references against form, field, organization, and session.
- A caller-supplied idempotency key.

Construct `finalData` from the schema:

```text
allowedFieldIds = fields from published schema
finalData = {}
for each allowed field:
    validate and normalize submittedData[field.id]
    add only that field to finalData
reject or audit every unknown submitted key
```

### 5.7 Layered rate limiting and abuse controls

Use multiple keys and layers:

- CDN/WAF limit before traffic reaches Node.
- Distributed Redis-backed application limiter.
- Per-IP + per-form limits.
- Per-session and verified-identity limits.
- Stricter limits for OTP send/verify, uniqueness checks, external validation, and DMS initiation.
- Submission velocity and anomaly rules at the business layer.
- Exponential delay or temporary blocks for repeated failures.
- Metrics and alerts by form/organization/ASN, not only IP.

Do not trust arbitrary `X-Forwarded-For`. Configure trusted proxy hops explicitly for the deployment and resolve one canonical client IP.

### 5.8 Separate legitimate machine integrations

If customers need API-driven submissions, provide a separate endpoint with:

- Hashed, revocable organization/form API keys or OAuth client credentials.
- Scopes such as `form:{id}:submit`.
- Per-key quotas.
- Key rotation and expiry.
- Audit logs.
- Optional IP allow-lists.
- The same schema and business validation as public submissions.

Do not place a reusable secret in public frontend JavaScript.

## 6. Recommended implementation plan

### Phase 0 — Confirm policy before coding

Decide for each form type:

- Is anonymous direct submission allowed?
- Must identity be verified?
- Must payment complete before acceptance?
- Are approved third-party integrations allowed?
- What submission volume is normal?
- Which deployments are active: Express, GCP, Lambda, and which database adapters?

This prevents a blanket authentication fix from breaking valid public use cases.

### Phase 1 — Low-risk request hardening

**Recommended first implementation sprint**

- Attach strict request validation to all three adapters.
- Make the shared service validate defensively even if an adapter forgets middleware.
- Reduce body size for public submissions.
- Reject/strip unknown field IDs.
- Add per-type field size limits.
- Correct proxy/IP handling.
- Add distributed per-form and per-IP rate limiting.
- Add structured security logging.
- Add idempotency support.

**Estimated scope:** 10–16 application files, approximately 400–800 lines including tests and adapter parity.  
**Database:** No migration is strictly required for validation/limits. Idempotency and durable security events benefit from a migration or Redis.

### Phase 2 — Real anti-bot verification

- Replace client math CAPTCHA with Turnstile/hCaptcha.
- Validate provider tokens in the backend.
- Apply to Express, GCP, and Lambda entry points through a shared service.
- Add provider keys/configuration and test keys.

**Estimated scope:** 6–10 files, approximately 200–400 lines including tests.  
**Database:** None required; Redis is optional for additional replay/session tracking.

### Phase 3 — Server-side respondent sessions and OTP

- Add public form sessions.
- Add real OTP send/verify endpoints.
- Bind drafts, DMS uploads, and submissions to the session.
- Remove hardcoded OTP and client-auth trust.

**Estimated scope:** 12–20 files, approximately 700–1,300 lines plus provider integration and tests.  
**Database:** One new session/challenge table plus indexes, or Redis with an audit table.

### Phase 4 — Payment integrity

- Add pending/paid/failed submission states.
- Create payment attempts server-side.
- Verify provider/POS webhooks.
- Update analytics and processing to operate on accepted/paid submissions.

**Estimated scope:** 12–22 files, approximately 800–1,600 lines plus integration tests.  
**Database:** Submission status fields and a payment-attempt table are recommended.

Estimates are directional. Supporting all Express, Lambda, and GCP adapters and all MySQL, Firestore, and MongoDB DAOs materially increases test and implementation scope.

## 7. Database changes

### Minimum hardening only

No database migration is required to:

- Enforce strict request validation.
- Reject unknown fields.
- Lower body limits.
- Verify Turnstile/hCaptcha.
- Add edge/Redis rate limits.

### Recommended durable model

#### `PublicFormSession` / `SubmissionIntent`

Suggested fields:

- `id`
- `formId` (indexed foreign key)
- `tokenHash` or `jti` (unique)
- `accessMode`
- `identityType` (`EMAIL`, `PHONE`, `USER`, `NONE`)
- `identityHash` (never raw identity unless required and protected)
- `otpHash` (nullable)
- `otpExpiresAt`
- `verificationAttempts`
- `verifiedAt`
- `captchaVerifiedAt`
- `expiresAt` (indexed)
- `consumedAt`
- `createdAt`
- Optional privacy-safe IP/network hash

#### `Submission` additions

- `status` (`PENDING_VERIFICATION`, `PENDING_PAYMENT`, `ACCEPTED`, `REJECTED`, `FAILED`)
- `source` (`PUBLIC_WEB`, `EMBED`, `INTEGRATION`), assigned by the server
- `publicSessionId` (nullable foreign key)
- `schemaVersion` or published form revision ID
- `idempotencyKey` (unique per form/session)
- `acceptedAt`
- `rejectionReason` (nullable, avoid sensitive values)

Suggested indexes:

- `(formId, status, createdAt)`
- `(formId, idempotencyKey)` unique
- `(publicSessionId)`

#### `PaymentAttempt`

- `id`
- `submissionId` (indexed foreign key)
- `provider` / `tenantId`
- `providerOrderId` (unique)
- `amountMinor`
- `currency`
- `status`
- `signatureVerifiedAt`
- `createdAt`, `updatedAt`, `expiresAt`

#### Optional `SubmissionSecurityEvent`

- `formId`, `sessionId`, `eventType`, `riskReason`, privacy-safe network hash, timestamp

Use this for operational detection without placing security telemetry inside user response JSON.

### Multi-database impact

This repository supports MySQL, Firestore, and MongoDB through DAO factories. Any durable model change requires:

- Prisma schema and MySQL migration.
- DAO interface updates.
- MySQL DAO implementation.
- Firestore DAO/document/index design.
- MongoDB DAO/index design.
- Backfill/default behavior for existing submissions.

## 8. Feature impact analysis

### Frontend

| Feature | Expected change |
| --- | --- |
| Public form submission | Send CAPTCHA/session/idempotency token and handle `401`, `403`, `409`, `422`, `429` |
| Embedded forms | Ensure provider widget and session flow work in allowed embed origins; avoid relying on third-party cookies |
| Form authentication | Replace hardcoded frontend OTP with backend start/verify flow |
| Payments | Create pending flow and wait for verified server status |
| Draft/save-and-resume | Bind draft access to verified public session instead of raw email/phone |
| File/signature upload | Bind DMS initiate/confirm/reference to form session and field |
| Multi-step/conditional fields | Server must mirror final visibility and required rules |
| Preview/review screen | Remains a UX feature, not a security boundary |
| Error handling | Add clear retry states for expired challenge/session, duplicate, throttled, and payment-pending responses |

### Backend

| Area | Expected change |
| --- | --- |
| Routes/controllers | New public route shape and equivalent Express/GCP/Lambda enforcement |
| Validation | Strict transport schema plus schema-derived field validation |
| Submission service | Verify all prerequisites and construct allow-listed data |
| Rate limiting | Distributed store and endpoint/form-specific policies |
| OTP | Provider integration, hashing, TTL, attempt limits |
| Payments | Server/POS order creation and signed webhook verification |
| DMS | Session-bound uploads and object ownership checks |
| Processing | Run assessment/voting/notifications only for accepted submissions |
| Logging | Security events with redaction; never log OTPs, tokens, payment secrets, or full response data |

### User management

- Anonymous respondents should not automatically become Keycloak users.
- Email/phone verification should create a short-lived **respondent session**, not an administrative account.
- Internal-only forms may use Keycloak and explicit form access rules.
- API integrations should use service credentials with form-scoped permissions.
- Organization owners need settings for access mode, quotas, allowed integrations, and abuse review.
- Identity retention, hashing, and deletion policies must be documented for privacy compliance.

### Existing behavior that may change

- Old bookmarks to published forms should continue to work.
- Existing anonymous forms can remain tokenless during a controlled compatibility period, but authentication/payment forms should fail closed.
- Automated scripts currently posting directly will stop unless migrated to a supported integration credential.
- Pending/unpaid submissions must be separated from accepted response counts.
- Strict unknown-field rejection may expose old clients sending stale field IDs; audit mode should precede enforcement.
- Lower body limits require DMS for large files/base64 payloads.
- Stronger rate limits may affect shared office/NAT networks; combine IP with session/form keys.

## 9. Safe rollout strategy

1. Add telemetry first: unknown keys, payload size, rate, form mode, and missing prerequisites. Do not log answers.
2. Add an `audit` mode that reports what strict enforcement would reject.
3. Add server-side validation and unknown-field rejection behind a feature flag.
4. Enable new CAPTCHA on test forms, then low-risk forms.
5. Implement respondent sessions and real OTP before claiming authenticated forms are secure.
6. Implement payment state/webhooks before treating payment forms as complete.
7. Migrate existing integrations to scoped credentials.
8. Enable enforcement by form mode.
9. Remove legacy tokenless paths after monitoring and customer notice.
10. Perform concurrency, replay, abuse, and cross-form tests before production rollout.

### Required test cases

- Unpublished, inactive, and expired forms reject submissions.
- Unknown field IDs are rejected or stripped according to policy.
- Missing required fields and invalid types fail server-side.
- Authentication-required form rejects anonymous direct requests.
- OTP cannot be reused, brute-forced, or applied to another form.
- CAPTCHA token cannot be reused or used for another configured hostname/action.
- Payment form never reaches `ACCEPTED` without a verified webhook.
- Duplicate idempotency keys produce one response only.
- Concurrent unique/voting requests cannot both win.
- DMS reference from another form/session is rejected.
- Rate limits operate across multiple app replicas.
- Express, GCP, and Lambda behavior is equivalent.
- MySQL, Firestore, and MongoDB adapters enforce the same invariants.

## 10. Anti-solutions to avoid

Do not implement these as the primary fix:

- Block Postman by User-Agent.
- Require `Origin`/`Referer` alone.
- Add a frontend secret or static custom header.
- Depend on CORS.
- Encrypt/obfuscate field IDs.
- Require a Keycloak login for all public forms.
- Keep the same CAPTCHA but hide the answer in minified JavaScript.
- Trust a browser-provided `paid: true`, `verified: true`, source, role, or identity field.
- Validate only in React.
- Add one global IP limiter and consider the issue closed.

These controls either break legitimate clients or are reproducible by an attacker.

---

## 11. Recommended first fix to implement later

For the best security-to-effort ratio, start with a small, compatible hardening slice:

1. Shared strict request parsing for Express, GCP, and Lambda.
2. Route-bound `formId` and a 512 KB public JSON limit.
3. Build stored data only from published schema field IDs.
4. Reject oversized values and malformed field types.
5. Redis-backed per-IP + per-form limits.
6. Turnstile/hCaptcha with mandatory server-side verification.
7. Security logging and idempotency.

This materially reduces spam, payload abuse, and data pollution without forcing users to create accounts. It does **not** complete authentication or payment security; those require the server-side session and payment phases described above.

## Final recommendation

Treat the current result as two separate facts:

1. **Public HTTP access is necessary** for anonymous forms and cannot be made browser-only.
2. **Security-sensitive form requirements are currently trusted to the browser**, so direct access can bypass authentication, CAPTCHA, payment, and intended workflow controls.

Do not add blanket login middleware to `POST /api/submissions`. Implement phased server-side enforcement based on explicit form access mode, beginning with strict schema-derived validation, payload/rate controls, and provider-verified anti-bot tokens; then add respondent sessions/OTP and payment state for forms that require them.
